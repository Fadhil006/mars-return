# MARS RETURN

A Mars mission rehearsal project for the NASA Space Apps Martian Map challenge: explore real terrain, compare routes, and ask **“Can we still get back?”** when a scenario changes.

**Status:** Working end to end. The backend prepares real NASA/USGS CTX terrain for Jezero Crater, loads the real Perseverance sampling sites and traverse, compares two route objectives, and calculates round trips, mid-walk rehearsals, a return envelope and a closure stress test, all with source citations. The React + Three.js planner shows this on a 2D map and in 3D terrain, with a grounded assistant brief and a mission report. See [data processing](docs/data-method.md) and [validation](docs/validation.md) for verified results and outstanding limits.

## Run it

Needs Python 3.12+, Node with npm, and about 450 MB of free disk space for the terrain download. **No API keys or accounts are required.**

On Linux or macOS, one command does everything (setup steps already done are skipped):

```sh
./run.sh                 # then open http://127.0.0.1:8000
```

Step by step (Windows, or to run each part yourself):

```sh
python -m venv .venv
.venv/bin/python -m pip install -r server/requirements.lock
.venv/bin/python -m scripts.prepare_demo      # first run downloads ~450 MB of USGS CTX data
cd web && npm ci && npm run build && cd ..
.venv/bin/python -m uvicorn server.api:app --host 127.0.0.1 --port 8000
```

Open http://127.0.0.1:8000 for the planner and http://127.0.0.1:8000/docs for the API. On Windows, use `.venv\Scripts\python` instead of `.venv/bin/python`. Use a browser with WebGL to see the 3D view; without it, the 2D map keeps working.

**Deploy (Render or any Docker host):** `docker build -t mars-return . && docker run -e PORT=8000 -p 8000:8000 mars-return`. The image prepares the terrain from the checksum-verified USGS files during the build and keeps only the ~1 MB prepared bundle. On Render, create a Blueprint from this repository (`render.yaml`, free plan). `.github/workflows/keep-alive.yml` pings `<RENDER_URL>/api/region` every 10 minutes once the repository variable `RENDER_URL` is set, so the free instance does not sleep.

Optional: set `MODEL_API_KEY` (an Anthropic key) in the server's environment to have the assistant write its explanations with a model. Without it, the assistant gives fixed-template explanations built from the same saved results.

## Development

Stack: Python/FastAPI with NumPy and Rasterio (pinned in `server/requirements.lock`), and React/TypeScript/Vite with Three.js (pinned in `web/package-lock.json`).

```sh
.venv/bin/python -m pytest server/tests          # backend tests
.venv/bin/python -m server.export_schema --check # shared schema matches the API models
cd web && npm run typecheck && npm test          # frontend checks
cd web && npm run dev                            # live reload at http://localhost:5173, /api proxied to :8000
```

The app runs locally and offline once the data is prepared. Synthetic fixtures are for development only and are never used as real terrain: if the terrain data is missing, the API returns 503. Keep downloaded rasters and generated bulk data out of Git, and keep secrets out of commits. The server reads `REGION_DATA_DIR` and `MODEL_API_KEY` from the process environment and never loads a `.env` file.

## Use of AI tools

In line with the NASA Space Apps rules on Super Intelligence (SI) tools:

- **Code and documentation:** written with the help of the AI coding assistant Claude (Anthropic), used through Claude Code. The team chose the challenge, designed the approach and reviewed, tested and validated the generated code (see `server/tests`, `web/tests` and [validation](docs/validation.md)).
- **In the app:** the mission assistant can optionally use a Claude model to word its explanations. It never calculates anything itself: it reads the saved plan's numbers, and a model answer is kept only if every number and citation matches that plan. Each answer lists every number it contains next to the stored value it repeats. Safety, hazard and radiation questions get fixed, never model-written answers that state what the planner does not model. Without a key, it uses fixed templates.
- **Data:** all terrain, imagery and sampling-site data come from NASA and USGS sources and are not AI-generated. The AI tools did not produce any NASA branding.

## Scientific scope

Use actual imagery/elevation for the region. The base, blocked corridor, speed, time budget and slope ceiling are hypothetical scenario inputs. Derived routes are model results, not certified astronaut navigation or safety guidance. Preserve missing-data masks and show data resolution.

## Related work and what is new here

MARS RETURN applies a long-standing human-exploration planning limit, the **walkback constraint**, to real Mars terrain: a crew must always be able to walk home if something fails.

- **Apollo and the NASA Walkback Test (2007):** Apollo-era planning assumed a 10 km maximum excursion, so a crew could still walk back if the rover failed. NASA tested suited walkback in 2007 ([report record](https://corpora.tika.apache.org/base/docs/govdocs1/515/515870.pdf)). Later work recalculated the walkback limit during an EVA from actual consumption ([Virtual Spacesuit, ICES 2018](https://ttu-ir.tdl.org/handle/2346/74208)).
- **SEXTANT (MIT, 2010):** a MATLAB traverse planner for the lunar south pole that finds efficient paths by distance, time or energy and computes the walkback from any point on a traverse ([AIAA SPACE 2010](https://core.ac.uk/works/6902634), [thesis](https://dspace.mit.edu/handle/1721.1/59560)).
- **NASA Mars Trek:** a web portal for 3D Mars terrain, distance and elevation-profile measurement ([Mars Trek](https://science.nasa.gov/science-research/planetary-science/mars-trek/)).
- **JPL traversability tools:** slope, rock and terrain-type cost maps used in Mars 2020 landing-site analysis ([paper](https://www-robotics.jpl.nasa.gov/media/documents/Data-driven%20surface%20traversability%20analysis%20for%20Mars%202020%20landing%20site%20selection.pdf)).

Everyday navigation apps shaped the interface. Like [Google Maps' fuel-efficient routing](https://blog.google/company-news/inside-google/around-the-globe/google-europe/eco-friendly-routing-in-europe/), it shows the fastest route beside an alternative and states the difference. Like [CalTopo](https://blog.caltopo.com/2013/01/16/slope-shading-revisited/), it shades the terrain by slope and breaks the trip into legs with time estimates. Like hikers' [turnaround times](https://www.outdoors.org/resources/amc-outdoors/features/the-right-time-to-bail-outdoor-safety-tips-every-hiker-should-know), it turns "return now or continue?" into a plain turnaround call.

What MARS RETURN adds, newest first:

- **Contact with base.** The route can fit the time budget and still take the crew out of sight of base for most of the walk. The planner computes line of sight from a hypothetical base mast over the real terrain, reports the longest continuous time out of contact (including time spent at a site the base cannot see), and checks it against a hypothetical contact rule, as Artemis EVA planning limits time without line of sight to the lander. On the default plan to Sid, the route fits with 1 h 16 min to spare but is out of sight for 1 h 03 min at a stretch. See [validation](docs/validation.md#contact-with-base-15-november).
- **Decide first.** In a rehearsal, the planner's options stay hidden until you make the call — return now, or continue — against a 10-second countdown. Then it shows how your call compares with its results. Committing before seeing an AI or model answer reduces over-reliance on it (Buçinca et al., CSCW 2021).
- **An assistant that proves its numbers.** Every number in an answer is shown with the stored plan value it repeats ("11 of 11 numbers traced to planner output"). A model answer with any number that is not in the plan is discarded.

It also runs in a browser on real Jezero CTX terrain and the real Perseverance sampling sites. It asks the walkback question *again when the scenario changes mid-walk*: rehearse a closed corridor, lost time or a slower pace, then compare "return now" with "continue, then return". It also shows the return envelope ("from where can we still walk home?"), stress-tests the way home against single closures, and has an assistant that explains results without ever calculating numbers itself.

## Data sources

- [M20 Jezero Crater CTX DEM 20 m](https://planetarymaps.usgs.gov/mosaic/mars2020_trn/CTX/ScienceInvestigationMaps_JPL/M20_JezeroCrater_CTXDEM_20m.tif) (USGS, NASA MRO CTX)
- [M20 Jezero Crater CTX orthomosaic 5 m](https://asc-pds-services.s3.us-west-2.amazonaws.com/mosaic/mars2020_trn/CTX/ScienceInvestigationMaps_JPL/M20_JezeroCrater_CTXortho_mosaic_5m.tif) (USGS, NASA MRO CTX)
- [Mars 2020 rover waypoints](https://mars.nasa.gov/mmgis-maps/M20/Layers/json/M20_waypoints.json) and [traverse](https://mars.nasa.gov/mmgis-maps/M20/Layers/json/M20_traverse.json) (NASA)
- [Perseverance Mars Rock Samples](https://science.nasa.gov/mission/mars-2020-perseverance/mars-rock-samples/) and [Location Map](https://science.nasa.gov/mission/mars-2020-perseverance/location-map/) (NASA)
- [PDS Geosciences Node: Mars 2020](https://pds-geosciences.wustl.edu/missions/mars2020/) and [PLACES bundle](https://pds-geosciences.wustl.edu/missions/mars2020/places.htm)
- Radiation: surface dose equivalent of 0.67 mSv/day measured by Curiosity's Radiation Assessment Detector (RAD) at Gale Crater, Aug 2012 to Jun 2013 ([Hassler et al. 2014, *Science*](https://doi.org/10.1126/science.1244797); [SwRI release](https://www.swri.org/press-release/swri-scientists-publish-first-radiation-measurements-surface-mars)). Used for a per-excursion dose estimate; measured at Gale, not Jezero.

Data kinds used: **optical** (CTX image), **topographic** (CTX elevation and the slope derived from it), **radiation** (MSL RAD), plus Perseverance sample and position records.

Full records with checksums and limitations are in `data/sources/`.
